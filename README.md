Школьный помощник на **Python + aiogram 3** плюс **Telegram Mini App**. Один бот на три разных задачи — режим выбирается одним вопросом при первой настройке:

| Режим | Для кого | Что внутри |
|---|---|---|
| 📖 **Личный дневник** | один человек в личке | свои уроки, своя домашка, свои напоминания. Ролей нет — некого ограничивать |
| 🏫 **Класс** | классный руководитель и класс | расписание и домашка на всех; новый класс сразу настроен так, что вносит учитель |
| 👩‍🏫 **Занятия с репетитором** | репетитор, ученик, родители | **без школьного расписания** — сами занятия и **оплата** с напоминанием, когда платить |

Режим меняет только то, какие разделы видно: ничего не удаляется, переключишь обратно — всё на месте. Права он не выдаёт и не отнимает, это отдельный механизм (см. [Права доступа](#-права-доступа)).

Существующие чаты обновление не заметят: у них режим не задан и вычисляется из типа чата (личка → дневник, группа → класс), что в точности повторяет прежнее поведение.

## ✨ Возможности

| | |
|---|---|
| 🚀 **Онбординг** | Шаг 1 — один вопрос: как ты будешь пользоваться (дневник / класс / репетитор). Дальше зависит от ответа: для дневника и класса — количество уроков, время звонков и расписание по дням (с опциональной субботой), для репетитора настройка на этом и заканчивается — школьного расписания там нет. Повторная настройка требует явного подтверждения и сохраняется одной атомарной транзакцией. Дефолты режима применяются только когда режим действительно меняется, поэтому повторный онбординг не сбрасывает то, что подкрутили руками |
| 📚 **Сегодня** | Сводка на день: уроки сегодня, домашка к сдаче, просроченные задания |
| 📅 **Расписание** | Просмотр расписания по дням недели с указанием времени уроков |
| 🗓 **Изменения по датам** | Разовые изменения школьного расписания на конкретную дату поверх недельного шаблона: отмена урока (показывается зачёркнутым), замена предмета, изменение времени, добавление разового урока, а также свободный день / праздник / каникулы / дистанционный день с примечанием. Шаблон при этом не меняется; перед сохранением показывается «сейчас → станет», удаление/очистка — с подтверждением. Итоговое расписание учитывается в «Сегодня» и в напоминаниях (в группе — только администраторам) |
| 🔀 **Чётная/нечётная неделя** | Чередование недель A (нечётная) и B (чётная). Неделя определяется не по номеру недели года, а по опорной дате-понедельнику (началу недели A), которая хранится в настройках чата. Обычное расписание можно скопировать в недели A и B и затем отредактировать различия; в редакторе видно, какая неделя правится. «Сегодня», расписание на завтра и напоминания автоматически выбирают нужную неделю. По умолчанию все чаты используют одно расписание (`all`) и работают без повторного онбординга. Изменения по датам имеют приоритет над недельным шаблоном (в группе — только администраторам) |
| 📝 **Домашние задания** | Добавление, редактирование и отметка о выполнении домашки по предметам и датам, архив выполненного, подтверждение перед безвозвратным удалением |
| 🎯 **Доп. занятия** | Кружки, репетиторы, секции и дополнительные уроки (например, английский в 18:00) — отдельно от школьных уроков. Еженедельные и разовые, с названием, временем (`18:00` или `18:00 - 19:00`), местом и примечанием. Просмотр доступен всем, изменение в группе — только администраторам. Показываются отдельным блоком в «Сегодня», в расписании выбранного дня и в напоминании на завтра |
| 💳 **Оплата занятий** | Только в режиме репетитора. За что платить, сколько, когда, как часто (разово / каждый месяц / за занятие) и за сколько дней напомнить. Суммы хранятся **целыми числами в копейках** — не float, деньги не накапливают ошибку округления; формат (`350 UAH`, `1 250,50 UAH`) считается один раз на сервере, поэтому бот и приложение не могут показать разное. Просроченное и «скоро» попадают в отдельное напоминание и в блок «💳 Об оплате» на экране «Сегодня». Видят все участники (просить платить и не показывать сумму — странно), меняют владелец и редакторы |
| ⏰ **Напоминания** | Отдельный экран (кнопка «⏰ Напоминания» или `/settings` → «⏰ Напоминания»): шесть независимо настраиваемых категорий: ДЗ на завтра, портфель на завтра, ДЗ в день сдачи (утром), изменения/отмены завтрашних уроков, напоминания о доп. занятиях (у каждого занятия — свой «за N минут», 0–10080) и напоминание об оплате (только в режиме репетитора). Категории, которых в этом режиме нет, не показываются: без школьного расписания «портфель на завтра» не о чем. Есть «тихие часы»: несрочные уведомления откладываются, но напоминание о занятии не приходит после его начала. Доставка идемпотентна (outbox с атомарным захватом), переживает перезапуск, безопасна при двух копиях бота, обрабатывает Telegram RetryAfter/Forbidden, старые задания периодически очищаются |
| 🌍 **Часовой пояс каждого чата** | У каждого чата свой часовой пояс (IANA, например `Europe/Kyiv`). От него зависят **все** пользовательские даты и время: «Сегодня», сроки сдачи ДЗ, чётные/нечётные недели, изменения по датам, доп. занятия и все напоминания — глобального часового пояса для пользовательских дат больше нет. Значение по умолчанию берётся из `TIMEZONE`, поэтому существующие чаты автоматически получают тот пояс, на котором и работали. Есть выбор популярных зон и ручной ввод; перед сохранением показывается текущее местное время. Неверная или устаревшая зона не останавливает планировщик — такой чат просто работает на поясе по умолчанию. Один проход планировщика корректно обслуживает чаты из разных поясов (у каждого своё «сегодня»/«завтра»), включая переходы летнего времени |
| 📎 **Фото и файлы в ДЗ** | К домашнему заданию можно приложить фотографию, документ или изображение как файл — до 5 вложений с необязательной подписью. Бот **не скачивает и не хранит сами файлы**: сохраняются только `file_id` / `file_unique_id` Telegram, тип, имя файла, размер и подпись. Ничего не распаковывается и не запускается, имя файла считается недоверенным (санитизируется и используется только для отображения). Вложения предлагаются сразу после описания в потоке добавления, добавляются и удаляются у существующего ДЗ (удаление — с подтверждением), а при открытии карточки присылаются вместе с ней. Если Telegram перестал принимать старую ссылку на файл, бот показывает понятное сообщение и предлагает приложить файл заново; одно «мёртвое» вложение не мешает отправке остальных. Удаление ДЗ каскадом удаляет его вложения |
| ✍️ **Авторство записей** | У домашних заданий, доп. занятий и изменений по датам сохраняется, кто их создал и кто изменил последним (Telegram-id и отображаемое имя) плюс время создания/изменения. В карточке ДЗ и доп. занятия автор виден сразу. Записи, созданные до появления авторства, честно помечаются как «Автор неизвестен» — авторство им не додумывается |
| 📜 **История изменений** | Журнал важных действий (⚙️ Настройки → «📜 История», в группе — только администраторам): кто и когда добавил, изменил, удалил, отметил выполненным или вернул запись. Постраничный просмотр с фильтром по типу событий. Удалённая запись исчезает, а безопасная строка аудита остаётся. В журнал не попадают токены, полные Telegram Update и лишние персональные данные — только id и имя автора, тип и id сущности, действие и короткое описание. Старые записи автоматически удаляются по настраиваемому сроку (`AUDIT_RETENTION_DAYS`, по умолчанию 180 дней) |
| ⚙️ **Настройки** | Общий экран (кнопка «⚙️ Настройки» или `/settings`): режим чата, часовой пояс, кто вносит данные, режим прав на изменение ДЗ, история изменений, данные и резервная копия, полный сброс. Строки, которые в этом режиме бессмысленны, не показываются. Управление уведомлениями — на отдельном экране «⏰ Напоминания» |
| ⌨️ **Команды и календарь** | Быстрые команды `/today`, `/schedule`, `/homework`, `/extra`, `/payments`, `/web`, `/settings`, `/help` (регистрируются в меню Telegram при запуске). Главное меню и справка показывают только те разделы, которые есть в этом режиме — кнопка, ведущая на пустой экран, хуже отсутствующей. При выборе даты сдачи ДЗ доступен компактный inline-календарь с листанием по месяцам, выделением текущего дня и запретом прошедших дат; ввод даты вручную (`ДД.ММ`) по-прежнему работает |
| 🛠 **Диагностика** | Команда `/status` (в группе — только администраторам) показывает версию приложения, состояние планировщика и время последнего тика, версию миграции БД и размер очереди напоминаний (ожидающие / в процессе / зависшие). Секреты (токен, `DATABASE_URL`, пути) не раскрываются |
| 🌐 **Приложение (Mini App)** | Всё то же самое экранами, а не диалогом: «Сегодня», расписание (просмотр + правка шаблона и разовых изменений по датам), домашка с добавлением/правкой/удалением, доп. занятия, оплата, настройки, участники и приглашения, история и экспорт. Пишет в ту же базу, что читает бот — отдельной синхронизации нет |
| 💬 **Личка и группы** | Работает как в личном чате, так и в общем чате класса — настройки хранятся отдельно на каждый `chat_id`, с разграничением прав (см. ниже) |

Под капотом — конечный автомат (FSM) для диалогов с персистентным хранилищем состояния, автоматическое разбиение длинных сообщений на части (лимит Telegram в 4096 символов), HTML-форматирование с экранированием пользовательского ввода, единый сервис времени (часовой пояс каждого чата + корректная обработка переходов летнего времени) и планировщик задач на APScheduler с outbox-таблицей для надёжной доставки.

## 🔐 Права доступа

Два независимых слоя, и они складываются. Всё проверяется **на сервере, до обращения к БД**, и обоими интерфейсами через одну функцию — `services.permissions.capabilities()`. Скрытая кнопка ничего не защищает: устаревшая `callback_data`, подложенное FSM-состояние или собранный руками HTTP-запрос будут отклонены.

### Слой 1: кто вообще может вносить данные

Определяется настройкой чата **«🔐 Кто вносит данные»** (⚙️ Настройки, в приложении — экран «Участники»):

- **👥 Как в Telegram** — по умолчанию и у всех чатов, существовавших до появления ролей. Права берутся из админства Telegram, ровно как раньше: администраторы меняют расписание, звонки, настройки, доп. занятия; обычный участник ведёт совместный список домашки, но не расписание и не занятия.
- **🔒 Только выбранные люди** — права берутся из выданной роли, а **админство Telegram больше не влияет**. В этом и смысл: в семейной группе половина участников — админы, и это ничего не должно значить.

Владелец чата (тот, кто прошёл настройку, — `chats.owner_user_id`) главнее обоих вариантов: **потерять доступ к своему чату нельзя**, даже включив ролевой режим и не выдав себе роль.

### Слой 2: роли (в ролевом режиме)

| Роль | Домашка | Доп. занятия | Оплата | Расписание | Участники |
|---|---|---|---|---|---|
| 👑 **Владелец** | всё | да | да | да | да |
| ✍️ **Редактор** | добавляет, правит, отмечает | да | да | нет | нет |
| 🎓 **Ученик** | **только отмечает выполненной** | нет | нет (но видит суммы) | нет | нет |
| 👀 **Только смотрит** | нет | нет | нет (видит суммы) | нет | нет |

Кому роль не выдали — тот «только смотрит». Роли выдаёт владелец на экране «Участники»; «владелец» в списке ролей отсутствует специально — владение следует за `owner_user_id`, а не выбирается из списка.

### Приглашения

Тем, кого нет в чате Telegram (например, родителю), доступ даётся **ссылкой-приглашением**: владелец выбирает роль, получает одноразовую ссылку с ограниченным сроком. Ссылка — это учётные данные, поэтому:

- в БД хранится только её хеш (как у токенов запуска и сессий) — из дампа базы рабочую ссылку не собрать;
- она одноразовая (атомарный `UPDATE … WHERE used_at IS NULL`) и истекает;
- роль зашита в приглашение при создании, поэтому активация не может дать больше, чем задумано;
- владелец может отозвать её до использования;
- ссылка показывается **один раз** — второй раз показать её физически нечем.

Приглашение принимается на бэкенде из подписанного `initData.start_param`, поэтому фронтенд не читает токен из недоверенных данных. Мёртвая ссылка не ломает вход: человек всё равно войдёт и просто не увидит класс — это лучше, чем цикл логина.

### Слой поверх: кто правит *чужую* домашку

Отдельная настройка `hw_edit_policy` **сужает** (никогда не расширяет) слой ролей:

- `collaborative` — **по умолчанию**, любой, кто вообще может править, правит любую запись;
- `creator_or_admin` — автор записи или админ. У записей без автора (созданных до появления авторства) сравнивать не с чем, поэтому они остаются доступны всем: иначе класс потерял бы доступ к своим же старым записям. Кому нужен строгий вариант — берёт `admin_only`;
- `admin_only` — только админы, включая записи без автора.

*Добавлять* домашку может любой, кому это разрешает слой 1. Удаление требует подтверждения («Удалить безвозвратно?»), чтобы случайный тап не уничтожал запись.

Отдельно от правки существует **отметка «выполнено»**: ученик может отметить домашку сделанной, не имея права её переписывать. В API это два разных ответа — `can_edit` и `can_complete`.

### Личные отметки о выполнении

Включается в настройках класса («Каждый отмечает выполненное за себя»). По умолчанию выключено, и тогда всё работает как раньше — одна общая галочка на чат.

Когда включено, это **слой поверх** общей отметки, а не замена:

- **общая отметка** (`homework.is_completed`) сохраняет смысл «задание закрыто для класса» и остаётся единственным, на что смотрят сообщения бота в чат и напоминания;
- **личная отметка** меняет только то, что видит этот человек в приложении, плюс счётчик «сделали N», который видит учитель.

Так сделано осознанно: сообщение в группу видят все, поэтому оно не может быть личным — и галочка одного ученика не должна выключать напоминание остальным двадцати девяти. В приложении кнопка меняет формулировку на «Я сделал» / «Я не сделал», чтобы не возникало иллюзии, что ты закрываешь задание для всего класса. Свою галочку может поставить любой, кто видит класс: она говорит о нём, а не о данных класса.

При отказе бот и приложение объясняют причину («🚫 В этом чате настройки меняет только владелец…»), а не игнорируют действие молча.

## 🏗️ Архитектура

Бот и приложение — **два адаптера над одним ядром**, а не две реализации. Расписание, права и время считаются в одном месте, поэтому разойтись не могут.

```
telegram-school-bot/
├── bot.py             # Точка входа: миграции, middleware, роутеры, планировщик
├── config.py          # Конфигурация из переменных окружения + валидация
├── utils.py           # Разбиение сообщений, HTML-экранирование, safe-парсинг callback_data
│
├── handlers/          # Адаптер Telegram: диалоги и команды
│   ├── onboarding.py     #   выбор режима + первичная настройка расписания
│   ├── today.py          #   сводка на сегодня (уроки, домашка, занятия, оплата)
│   ├── schedule.py       #   просмотр и редактирование расписания
│   ├── date_overrides.py #   изменения по датам (отмены/замены/праздники)
│   ├── homework.py       #   CRUD домашних заданий + вложения
│   ├── extra.py          #   CRUD доп. занятий (кружки/репетиторы/секции)
│   ├── payments.py       #   💳 Оплата: список и отметка «оплачено»
│   ├── settings.py       #   ⏰ Напоминания и ⚙️ Настройки (режим, пояс, права, сброс)
│   ├── history.py        #   📜 История изменений (журнал аудита)
│   ├── data_backup.py    #   экспорт/импорт данных чата
│   ├── web.py            #   /web — одноразовая ссылка в Mini App
│   ├── migration.py      #   миграция group → supergroup
│   ├── status.py         #   /status — диагностика для администраторов
│   └── common.py         #   /start, /help, /cancel + команды разделов
│
├── web_api/           # Адаптер HTTP (FastAPI). Никогда не импортирует handlers/
│   ├── main.py           #   сборка приложения, CORS, гейт OpenAPI
│   ├── deps.py           #   сессия → пользователь → доступ к классу + возможности
│   ├── security.py       #   проверка initData, хеширование токенов
│   ├── settings.py       #   типизированная конфигурация веба
│   └── routers/          #   auth, classes, dashboard, schedule, homework, extra,
│                         #   payments, members, settings, audit, export, health
│
├── application/       # Общий слой между адаптерами
│   ├── dto.py            #   Pydantic-DTO — единственное, что уходит по сети
│   └── queries.py        #   use-cases: ORM → DTO, проверки прав перед записью
│
├── services/          # Домен, общий для бота и API
│   ├── profiles.py           #   режим чата: что показано и какие дефолты
│   ├── permissions.py        #   ЕДИНЫЙ источник прав: роли + режим доступа + политика ДЗ
│   ├── effective_schedule.py #   итоговое расписание (шаблон + изменения + недели A/B)
│   ├── timeservice.py        #   время и даты: пояс чата, DST, тихие часы
│   ├── extra_activities.py   #   фильтрация занятий по дате/дню
│   ├── audit.py              #   авторство и журнал (безопасные краткие записи)
│   ├── attachments.py        #   вложения ДЗ (только ссылки Telegram)
│   ├── status.py             #   безопасная диагностика для /status
│   └── scheduler.py          #   6 категорий напоминаний + идемпотентный outbox
│
├── keyboards/         # Reply/inline клавиатуры (меню зависит от режима чата)
├── middleware/access.py  # контекст чата, guard онбординга, ролевой require_admin
├── database/          # SQLAlchemy-модели, async-доступ, FSM-хранилище, миграции
├── alembic/           # Версионируемые миграции схемы
├── web/               # Frontend: React + TypeScript + Vite
└── tests/             # pytest: БД, хендлеры, планировщик, права, HTTP-слой
```

**Правила, которые держат это в форме:**

1. **Права — только в `services/permissions.py`.** Бот и API вызывают одну функцию; `middleware.access.require_admin` тоже ходит через неё, поэтому все ~30 админских действий бота автоматически подчиняются ролевому режиму.
2. **API отдаёт только DTO из `application/dto.py`.** ORM-объекты не сериализуются никогда, поэтому новая колонка не может утечь по сети.
3. **`application/` не импортирует `handlers/` и `keyboards/`** — это адаптер Telegram, а общий слой не должен от него зависеть.
4. **Новые колонки — nullable или с server-default.** `NULL` всегда означает «как было раньше»: незаданный режим чата, незаданный режим доступа, невыданная роль.
5. **Каждый запрос к БД скоупится по `chat_id`.** Чужой id записи даёт 404, а не чужие данные.

**Стек:** aiogram 3, SQLAlchemy 2 + aiosqlite, Alembic, APScheduler, pytz, FastAPI, React 18 + Vite.

**Поддерживаемая БД:** только SQLite (`DATABASE_URL` обязан начинаться с `sqlite`) — осознанное ограничение, зафиксированное в `config.py`.

## ⚙️ Установка и запуск

### Локально

```bash
git clone https://github.com/blikzes-bit/telegram-school-bot.git
cd telegram-school-bot

uv sync --all-extras --dev    # окружение по pyproject.toml + uv.lock

cp .env.example .env          # укажи свой BOT_TOKEN

uv run alembic upgrade head   # поднять схему БД (отдельный шаг, см. ниже)
uv run python bot.py
```

Схему нужно поднять **до** первого запуска: `uv run alembic upgrade head`. Бот миграции не применяет — он лишь проверяет, что база на актуальной ревизии, и отказывается стартовать с понятной ошибкой, если это не так (см. раздел «Миграции БД» ниже).

### Docker

Готовый мультиархитектурный образ (`amd64` + `arm64`) публикуется в GHCR при каждом пуше в `main`. Не содержит тестов, dev-инструментов и Node, запускается от непривилегированного пользователя.

У образа **три роли**, задаются командой. Бот и API делят `database/models.py` и слой сервисов, поэтому едут одним тегом — так между ними не может возникнуть расхождения версий.

```bash
# 1. Накатить миграции и выйти. Отдельным шагом, а не побочным эффектом
#    старта бота, — после него бот и веб можно поднимать в любом порядке.
docker run --rm -v school_bot_data:/data \
  ghcr.io/blikzes-bit/telegram-school-bot:latest migrate

# 2. Бот
docker run -d --name school-bot \
  -e BOT_TOKEN=your_token_here \
  -e TIMEZONE=Europe/Kiev \
  -v school_bot_data:/data \
  --health-cmd "python -c \"import os,sys,time; p=os.environ['HEARTBEAT_FILE']; sys.exit(0 if os.path.exists(p) and time.time()-os.path.getmtime(p)<150 else 1)\"" \
  ghcr.io/blikzes-bit/telegram-school-bot:latest bot

# 3. Mini App: API и собранный фронтенд с одного origin
docker run -d --name school-web \
  -e BOT_TOKEN=your_token_here \
  -e APP_ENV=production \
  -e SESSION_SECRET=... \
  -v school_bot_data:/data -p 8000:8000 \
  --health-cmd "python -c \"import urllib.request,sys; sys.exit(0 if urllib.request.urlopen('http://localhost:8000/api/v1/health').status==200 else 1)\"" \
  ghcr.io/blikzes-bit/telegram-school-bot:latest web
```

`HEALTHCHECK` не зашит в образ намеренно: роли проверяются по-разному (бот обновляет `HEARTBEAT_FILE`, API отвечает на `/api/v1/health`), а директива статическая — поэтому проверка задаётся на контейнере.

За обратным прокси роли `web` нужен `FORWARDED_ALLOW_IPS` с адресом прокси, иначе ограничитель попыток входа увидит один и тот же IP у всех запросов и превратится в общий лимит на всех пользователей.

**`SESSION_SECRET` должен совпадать у бота и у веба.** Бот хеширует им одноразовый токен запуска, API по этому же хешу его ищет — если значения разойдутся, вход будет молча падать с «launch token is invalid».

База данных хранится в `/data/school_bot.db` — том нужен для сохранения данных между перезапусками контейнера.

## 🌐 Веб-версия (Mini App)

**Telegram Mini App** поверх той же базы и той же доменной логики — не отдельное приложение с синхронизацией, а второй интерфейс. Что записали в приложении, бот покажет в `/today`, и наоборот.

Внешний вид — чёрно-золотой, осознанно фиксированный: приложение не перекрашивается под тему клиента, но есть два полноценных варианта (тёмный и светлый), а не один плюс инверсия.

**Как открыть:** в чате выполни `/web` — бот проверит, что ты участник, и выдаст одноразовую кнопку. Открыть приложение для произвольного `chat_id` нельзя: без подтверждённого членства любой запрос к данным класса получает `403`.

### Что умеет приложение

| Экран | Что можно |
|---|---|
| **Сегодня** | уроки, домашка (к сдаче / просроченная / ближайшая), занятия, оплата |
| **Расписание** | три режима: неделя как она будет, обычный недельный шаблон (звонки + предметы, недели A/B), изменения на конкретную дату (свободный день, отмена урока, замена, другое время) |
| **Домашка** | добавить, изменить, удалить (в два тапа с подтверждением), отметить выполненной; фильтры актуальное/просроченное/выполненное |
| **Занятия** | полный CRUD кружков, репетиторов, секций |
| **Оплата** | только в режиме репетитора: за что, сколько, когда, отметка «оплачено» |
| **Участники** | роли, режим доступа, ссылки-приглашения, отзыв доступа (у владельца) |
| **Настройки** | режим чата, название, часовой пояс, права на ДЗ, напоминания, история, экспорт |

Каждый экран показывает только то, что есть в этом режиме чата, и только те кнопки, которые сработают: возможности приходят с сервера (`permissions`, `can_edit`, `can_complete`), и сервер их перепроверяет при записи.

### Безопасность

- Вход только по подписанной `initData` (официальный алгоритм HMAC), с проверкой свежести. `initDataUnsafe`, query-параметры и `localStorage` не доверяются никогда.
- Ссылка запуска — 256-битная случайная, хранится **только хешем**, одноразовая, живёт минуты и привязана к паре (пользователь, чат).
- Сессия — opaque cookie (`HttpOnly`, `SameSite=Lax`, `Secure` в продакшене); в БД лежит только хеш.
- `POST /auth/telegram` ограничен по частоте с одного IP.
- Из персональных данных хранятся только Telegram-id и отображаемое имя. Ни username, ни телефон, ни сырой Update.

```

Фронтенд (React + Vite):

```

Всё сразу в Docker (только для разработки, не заменяет продакшн-образ бота):

```bash

```

### Проверки фронтенда

```bash

Горизонтальное масштабирование требует перехода на PostgreSQL; фабрика сессий в `database/db.py` специально устроена так, чтобы это была замена инфраструктуры, а не переписывание API.

## 🗃️ Миграции БД

Схема версионируется через **Alembic** (`alembic/`) вместо ручных `ALTER TABLE`.

Применение миграций — **отдельный шаг**, а не побочный эффект старта бота. Так бот и веб-приложение можно поднимать в любом порядке, и видно, что миграция прошла, до того как что-то живое стартовало:

```bash
uv run alembic upgrade head                                   # из чекаута
docker run --rm -v <данные>:/data <образ> migrate             # в Docker
```

Бот при старте только сверяет ревизию базы с ожидаемой. Если база отстала, он не стартует и печатает, что именно не так и как это починить, — вместо невнятного «no such table» позже, посреди работы обработчика.

Для **существующей** продакшн-базы, созданной до внедрения Alembic (т.е. любой `school_bot.db`, работавший со старой версией бота), перед первым запуском новой версии один раз выполните:

```bash
alembic stamp e42f61dd6f2f   # baseline-ревизия, соответствующая старой схеме
alembic upgrade head          # применит constraints/индексы/outbox/FSM-таблицы
```

### Миграция group → supergroup

Когда Telegram обновляет обычную группу до супергруппы, chat_id меняется. Бот отслеживает системное сообщение об этом и переносит все данные на новый chat_id в одной транзакции — вручную ничего переносить не нужно. Переносится всё: расписание и звонки, недели A/B, домашние задания (вместе с авторством и вложениями), доп. занятия, изменения по датам, оплата, настройки напоминаний, часовой пояс, режим чата, режим доступа, роли участников и журнал истории изменений.

## 🔄 Обновление, бэкап и диагностика

**Обновление существующей установки:**

```bash
git pull                       # забрать новую версию
docker compose up -d --build   # пересобрать и перезапустить (или перезапустить процесс)
```

Перед запуском новой версии примените миграции шагом `migrate` (см. «Миграции БД»). `.env` и `BOT_TOKEN` остаются прежними.

**Резервное копирование и восстановление** (в чате): «⚙️ Настройки» → «💾 Данные и резервная копия».
- 📦 JSON — полная копия чата (расписание, звонки, недели A/B, изменения по датам, доп. занятия, ДЗ, настройки, часовой пояс). Токен, содержимое файлов и FSM в копию не попадают; для вложений сохраняются только `file_id` + метаданные (Telegram не гарантирует их вечную переносимость между ботами).
- 📊 CSV — расписание для Excel/Google Таблиц; 📅 ICS — уроки/занятия/сроки ДЗ в календарь.
- Импорт JSON — только для админа группы, режимы `merge`/`replace` (для `replace` — двойное подтверждение), одной транзакцией с откатом при ошибке; целевой чат всегда текущий.

**Диагностика:** команда `/status` (в группе — только админам) показывает версию приложения, состояние планировщика, время последнего тика, версию миграции БД и размер очереди напоминаний. Секреты не раскрываются.

**Troubleshooting:**

| Симптом | Что проверить |
| --- | --- |
| Бот не отвечает после `git pull` | Логи старта: применились ли миграции; корректен ли `BOT_TOKEN` в `.env` |
| Не приходят напоминания | `/status` — планировщик «работает» и свежий «последний тик»; часовой пояс чата в «⚙️ Настройки»; тихие часы |
| Docker `HEALTHCHECK` красный | Обновляется ли `HEARTBEAT_FILE` (планировщик тикает раз в минуту) |
| Зависла форма (FSM) | Отправить `/start` или «❌ Отмена» — состояние сбросится |
| «Кнопка устарела» | Открыть раздел заново: старые callback-кнопки безопасно отклоняются |

## 🧪 Тесты и качество кода

```bash
uv run pytest                              # полный набор тестов (сейчас 650)
uv run pytest --cov=. --cov-report=term-missing  # с покрытием
uv run ruff check .                        # линт
uv run mypy .                              # проверка типов
uv audit --frozen --no-dev                 # аудит зависимостей на уязвимости
```

Тесты покрывают: часовой пояс каждого чата (Europe/Kyiv, UTC, America/New_York, разные календарные даты у чатов в один и тот же момент, переходы летнего времени — несуществующее и повторяющееся локальное время, отсутствие двойного напоминания, неизвестная зона не ломает планировщик), вложения ДЗ (FSM добавления, несколько файлов, лимит и дубликаты, удаление с подтверждением, каскад при удалении ДЗ, изоляция по `chat_id`, права, недоверенное имя файла, ошибки Telegram API на «мёртвом» `file_id`), работу с БД и конкурентный `get_or_create_chat`, атомарность онбординга и переконфигурации, поведение до `/start` и после полного сброса, права доступа участник/админ в группе, все три режима прав на ДЗ (админ / автор / другой участник, включая старые записи с `NULL`-авторством), авторство и журнал аудита (в том числе то, что удалённая запись оставляет строку истории, а журнал изолирован по `chat_id` и экранирует HTML), безопасный HTML-рендеринг, устаревшие/битые callback-кнопки, edge-cases дат (29 февраля, просроченные быстрые кнопки), outbox-доставку напоминаний (частичный сбой, `RetryAfter`, `Forbidden`) и миграцию group → supergroup.

Отдельно закреплены свойства, которые легко потерять при доработках:

- **режимы чата** — `NULL` ведёт себя как раньше, незнакомое значение откатывается к разумному, переключение режима не удаляет данные, дефолты применяются только при реальной смене режима;
- **роли** — в режиме «как в Telegram» и админ, и обычный участник получают в точности прежние права (включая то, что доп. занятия были только для админов); в ролевом режиме админство Telegram перестаёт влиять, а владельца нельзя запереть снаружи;
- **приглашения** — одноразовость, истечение, отзыв, невозможность отозвать чужое, приглашение внутри подписанной `initData`, и то, что мёртвая ссылка не ломает вход;
- **расписание в вебе** — правка шаблона не путается с изменением на дату и наоборот; несогласованное время звонков отклоняется целиком;
- **оплата** — суммы остаются целыми, формат считается на сервере, напоминание охватывает ровно то, что подсвечено как «скоро», а чат без записей не получает сообщений;
- **фронтенд** (38 тестов, vitest + RTL) — вкладки и разделы следуют режиму, удаление требует подтверждения, а при `can_edit: false` кнопок правки просто нет.

GitHub Actions прогоняет полный CI (линт + типы + тесты + аудит) на каждый pull request, а тесты — перед публикацией Docker-образа.

## ⚠️ Известные ограничения

- Только SQLite — другие БД не поддерживаются и явно отклоняются при старте.
- Троттлинг отправки напоминаний — простая пауза между сообщениями, не полноценный token-bucket.
- Часть межчатовых запросов планировщика (по чатам целиком) не батчится в один SQL-запрос — при очень большом числе чатов возможен рост числа запросов к БД.
- Ограничение частоты входа в приложение живёт в памяти процесса: при нескольких копиях API нужен общий счётчик.
- Личные отметки о выполнении есть только в приложении: сообщения бота в чат по своей природе общие, поэтому персональные напоминания в ЛС пока не реализованы.
- В приложении нет обучающего тура при первом входе.
- Добавление и правка записей об оплате — только в приложении; бот показывает список и отмечает оплаченное.
